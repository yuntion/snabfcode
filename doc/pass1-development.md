# Pass 1 开发报告：全图旋转密钥复用如何改变第一层

2026-11-19 · 服务器 `/home/fhecompiler` · 范围：论文 Pass 1

**结论：** 在同一条 `Linear → SiLU → Linear` 链路上，后层要用哪些旋转密钥，已经能改变前层实际执行的密文路由。在专门构造的 64×64 双步长复用负载上，原生 HEIR、逐层规划、全图规划分别生成 **5、4、3 把** Galois 密钥。全图比原生少 **20,973,248 字节（40%）**，比逐层少 **10,486,624 字节（25%）**。这是对生成密钥调用 `MarshalBinary()` 得到的长度，不是估算的内存峰值。

## 1. 三组工作负载，三个执行方案

| 模型 | HEIR 提取的非零对角线（第 1 层；第 2 层） | 原生 HEIR | 逐层 Pass 1 | 全图 Pass 1 |
|---|---|---:|---:|---:|
| `control`，原 4×4 对照 | `{0,1,2,3}`；`{0,1,3}` | 2 把 | 3 把 | 2 把 |
| `strided64`，单步长复用 | `{0,1,2,5}`；`{0,4}` | 3 把 | 4 把 | 3 把 |
| `reuse64`，双步长复用 | `{0,7,9}`；`{0,6,8}` | 5 把 | 4 把 | 3 把 |

两个 64×64 模型通过项目的 `src/frontend/snabf_frontend/strided.py` 导入：生成完整的公开权重矩阵与带 secret 输入的 Linalg 图，再经过和对照组相同的 HEIR lowering。行权重随位置变化，因此把明文掩码旋错方向也会造成数值错误。没有向求解器手填对角线。三个方案冻结相同的 `N=16384`、具体 `Q/P`、SiLU 求值 DAG 和编码布局。

**为什么第一层会变？** 以 `reuse64` 为例，第一层单独优化时直接旋转 `7` 和 `9`。放入全图后，第二层本来就需要 `6` 和 `8`，第一层因此改写为 `7=6+1`、`9=8+1`：两次 hoisted baby 旋转复用已有密钥，再对同一组的部分和旋转一次 `1`。最终全图只需 `{1,6,8}`；其中 `6` 和 `8` 的引用计数都是 2。`strided64` 也改变了第一层，但全图密钥数只追平原生 HEIR。两个结果都保留。

## 2. 论文公式如何进入执行

| 环节 | 实现与可核对产物 |
|---|---|
| 前端与预算 | `src/frontend` 继续扩展 `extern/heir/frontend`。`src/compiler/pass1/heir_ir.py` 读取真正的 `prepare_linear_transform`，沿 `store → load → apply` 绑定 SSA。Orchestrator 登记具体 profile、输入层级、编码槽数和明文掩码 scale `q[ℓ]`；它不是密文 scale。三组链路两层的 `ℓ` 均为 7 和 2。 |
| 公式 (2) | `src/compiler/pass1/Planner.cpp` 复用已有 C++ 子群塔枚举器与 HiGHS 选择器。在物理旋转群 `Z₈₁₉₂` 中搜索；实际编码只有 4096 槽。稀疏层不执行空陪集。逐层和全图共用候选、相同的操作单价及序列化密钥尺寸，逐层方案最终也按真实物理并集统计。 |
| 发射与运行 | 将 `(diagonal,baby,giant)` 三元组和塔层写回 MLIR，重建 Galois 密钥清单并交给 `heir-opt` 重验。`goemit` 将官方翻译器生成的线性变换绑定到 `src/backend/tower`。该核在 4096 个槽上预先编码逆旋掩码，在线调用 `RotateHoistedNew`、明文乘加和 giant 旋转；后续 rescale 仍由 HEIR 生成。不是修改 BSGS 比例让 Lattigo 再决定一次。 |
| 公式 (3) | `src/compiler/pass1/bootstrap.py` 用 `N·σkey²·ΣPj²/12` 选择下游预算档，比较 `Cboot(N,ℓ)−β·Cboot(N′,ℓ−1)` 和 `Cdown+β·Cup+ΔCdown`。收益必须严格为正，布局必须可保值。 |

本轮是**项目编译器扩展**：采用锁定版本 HEIR 的 CLI 验证和翻译，不依赖一个声称已注册的上游 `--snabf-pass1`。发射范围为一个物理密钥族、静态布局、每个已准备变换对应一次应用；未建模的 Galois 消费者会在替换密钥清单前被指出。

## 3. 数值与成本口径

每组模型每个方案固定 64 个公开输入，独立生成加密随机量；4×4 用全部 16 个角点及 48 个随机输入；64×64 用 4 个结构化输入、12 个单点输入和 48 个随机输入。浮点对照直接取原始 Linalg 矩阵，在 float64 中计算 `W₂·SiLU(W₁x)`。同时逐槽比较两个规划方案与原生 HEIR 的解密输出。精度门限统一为 `2^-12 = 0.000244140625`；每次核对实际级数 `7 → 0` 和输出 scale 的一致性。

三组 × 三方案合计 **576 次密文推理、25,344 个输出**。逐臂 MSE、最大误差、与原生 HEIR 的最大差、序列化字节数和计时见 [原始数值 JSON](pass1-results/metrics.json)。计时只包含生成程序的在线密文求值，不含生成密钥、预处理、加解密。

| 工作负载 | 全图最大绝对误差 / MSE（对真 SiLU） | 全图与原生的最大绝对差 | 在线平均 ms：原生 / 逐层 / 全图 |
|---|---:|---:|---:|
| `control` | 6.78×10⁻⁵ / 2.05×10⁻¹⁰ | 6.06×10⁻⁵ | 158.2 / 154.2 / 157.9 |
| `strided64` | 5.32×10⁻⁵ / 7.93×10⁻¹¹ | 5.57×10⁻⁵ | 170.3 / 143.3 / 155.2 |
| `reuse64` | 4.51×10⁻⁵ / 6.26×10⁻¹¹ | 6.26×10⁻⁵ | 176.7 / 138.0 / 161.7 |

原基线测试另行重跑：64/64 次、256 个输出，最大误差 5.03×10⁻⁵，MSE 1.63×10⁻¹⁰；DownConv 原有回归也通过。这部分不重复计入上面的 576 次。

规划时固定 `Choist(ℓ)=0.625(ℓ+1)`、`Cks(ℓ)=ℓ+1`、`η=1` 成本单位/MiB；一把完整 Q/P 旋转密钥实测为 **10,486,624 B**。这些操作单价是公开的归一化输入，不是机器时延。`reuse64` 上逐层与全图方案的目标值为 53.753296 和 51.752472；后者多做一次外层旋转，换取较少的常驻密钥。不能将目标值降低解释成相同比例的加速。

## 4. 环切自举判定

三个推理模型没有 bootstrap 节点，计划中均记为 `not_applicable`。另有含真实 `lattigo.ckks.bootstrap` 的 HEIR 模块，用 `--lattigo-configure-crypto-context` 验证并配置后，通过同一规划入口产生 [bootstrap 计划](pass1-results/boot/plan.json)。在记录的输入预算下，`N=16384 → N′=8192`，`ℓ=3 → 2`，`β=1`，方差增量 5，节省 40、罚金 35，**判定启用，余量 +5**。这是使用指定成本表的编译决策，不是环切 bootstrap 的实测耗时。回归还覆盖平局拒绝、负收益、下游方差超额、层级不足和不相容布局。整个环切 bootstrap 的密文执行仍留给后续转换后端。
